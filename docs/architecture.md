# Архитектура защищённого мессенджера

Статус: черновик этапа 0 (до кода). Изменения только через подтверждение владельца.

## Принципы
1. Проверенные библиотеки: libsignal (протокол), liboqs (пост-квантовые примитивы), SQLCipher. Своей криптографии нет. Если нужной функции нет в библиотеке, работа останавливается и вопрос идёт владельцу.
2. Приватность важнее удобства. Любой выбор между ними записывается в `docs/decisions/` и согласуется.
3. Сервер глупый: хранит зашифрованные блобы и минимум служебных данных. E2E-криптографии на сервере нет.
4. Протокол конверта закладывается в этапе 1 и не меняется в этапе 2 (меняется только транспорт).

## Компоненты

```
Клиент A ──(этап 1: WSS; этап 2: Tor onion)──► Сервер (старый Android, Termux) ◄── Клиент B
   │  E2E: PQXDH + Double Ratchet                 │ SQLCipher: ящики, пакеты (TTL),
   │  внутри конверта: метаданные + содержимое    │ ключи ящиков, публичные ключи устройств,
   │  снаружи: одноразовый ID, TTL                │ запись суперадмина
   ▼                                              ▼
SQLCipher на клиенте (история, сессии,          ключ БД вводится при старте, не лежит
mesh-буфер); главный ключ в Android Keystore    рядом с файлом
```

### Сервер (`server/`)
- Python, FastAPI + WebSocket (ADR-002), Termux на выделенном телефоне.
- Модули: `api` (ящики, пакеты, регистрация устройств), `db` (SQLCipher, только параметризованные запросы), `admin` (токен привязки, проверка подписей суперадмина), `limits` (валидация формата и размера, TTL-очистка), `logging` (фильтр: без IP, ключей и тел пакетов).
- Процесс работает от отдельного пользователя с доступом только к файлу БД.

### Клиент (`client-android/`)
- Kotlin, только Android. Модули: `app` (UI), `core-crypto` (обёртка над libsignal/liboqs), `core-storage` (SQLCipher, Keystore), `core-net` (транспорт), `core-security` (автоблокировка, FLAG_SECURE, проверка root/debug).
- Все строки в ресурсах (`values`, `values-ru`), темы светлая/тёмная, язык ru/en.

## Криптография (ADR-001)
- Установка сессии: PQXDH как в Signal (X25519 + ML-KEM-1024), затем Double Ratchet.
- Подписи в протоколе: классические Ed25519/XEdDSA, как в libsignal.
- ML-DSA (liboqs) используется только для подписи действий суперадмина, вне протокола libsignal.
- Отпечатки ключей сверяются вручную, QR одноразовый, смена ключа собеседника показывает явное предупреждение.

## Конверт (спецификация в `protocol/`)
- Фиксированная длина. Снаружи: одноразовый ID, версия, TTL-класс. Всё остальное (отправитель, адрес, тип) шифруется внутри.
- Файлы: случайный ключ на файл, ключ передаётся внутри E2E-сообщения; куски фиксированного размера, SHA-256 каждого куска и файла целиком.
- Голосовые сообщения идут как обычные зашифрованные файлы.

## Ящики и адресация (этап 2, формат закладывается в этапе 1)
- У участника ящик со случайным ключом, выданным при личном знакомстве (QR). Отправитель кладёт пакет в ящик, получатель забирает по ключу. Ключи ящиков меняются периодически.
- Sealed sender: схема на основе ключей ящиков, а не серверных сертификатов Signal. Открытый вопрос, требует отдельного ADR перед этапом 2.
- Группа: отдельная копия для каждого участника, случайные задержки отправки.

## Суперадмин (этап 3, минимальная часть в этапе 1)
- Токен привязки создаётся только физически на телефоне-сервере, показывается на его экране, одноразовый.
- Дальше вход по подписи ключа из Keystore плюс биометрия/PIN. Привязка к одному устройству. Действия подписываются.

## Этапы
| Этап | Содержание |
|---|---|
| 1 | Чат через сервер, E2E, файлы, автоудаление, защита экрана, минимальный суперадмин |
| 2 | Tor, мосты, cover traffic, ящики, sealed sender, группы |
| 3 | Усиление сервера: диск, фаервол только через Tor, полный суперадмин |
| 4 | Mesh |

После каждого этапа выполняются проверки безопасности (`docs/security-checks/`).
