# Этап 1, модуль «сервер»: отчёт

Тесты: `cd server && python -m pytest` (30 проходят, Python 3.13, Linux x86_64).

Сделано: SQLCipher (ключ 32 байта hex, из файла вне каталога данных или вводом), подписанные запросы Ed25519 с защитой от повтора, ящики, пакеты фиксированного размера, TTL-очистка, префикс-ключи (PQXDH блобы, непрозрачные для сервера), WS-сигнал, токен привязки суперадмина, CLI сброса суперадмина, строгая валидация, ограничение тела, логирование с редактированием.

Проверено тестами: шифрование файла БД и отказ при неверном ключе; одноразовость токена; отклонение повтора, устаревшей метки, подмены тела и пути; отказ для пользователя на админ-путях; каскадный отзыв при удалении пользователя; одинаковый ответ при неверном токене и несуществующем ящике; только точный размер конверта; отсечение больших тел; SQL-подобные идентификаторы; запуск реального процесса с проверкой, что его вывод без IP, ключей и токенов (токен только один раз на консоли).

## Не проверено / ограничения
- Termux на aarch64: `sqlcipher3-binary` даёт wheel для manylinux, под Android/bionic его, вероятно, придётся собирать самому. Нужна проверка на телефоне.
- Процесс в Termux работает под тем же Android-UID, что и файлы данных, отдельного пользователя нет (ADR-002).
- Ключ БД после ввода находится в памяти процесса.
- Отправитель пакета виден серверу как подписавшее устройство (до sealed sender в этапе 2). Метаданные «кто в какой ящик» сейчас доступны серверу.
- Блокировка привязки по неудачам и nonce-кэш живут в памяти и сбрасываются при перезапуске.
